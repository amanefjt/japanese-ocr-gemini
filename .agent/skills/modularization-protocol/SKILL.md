# 実行計画の策定 (Writing Plans)

## 概要
コードに触れる前に、エンジニアにコンテキストが全くないことを想定して、包括的な実装計画を作成します。すべてのステップは、2-5 分程度で完了する「一口サイズ」のタスクに分解される必要があります。

## 基本ルール
1. **開始時の宣言:** 「writing-plans スキルを使用して、実装計画を作成しています。」
2. **保存場所:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
3. **DRY, YAGNI, TDD:** 重複を避け、不要な機能を作らず、テスト駆動で進める。

## タスクの粒度
- 「失敗するテストを書く」 - 1ステップ
- 「実行して失敗を確認する」 - 1ステップ
- 「テストをパスさせる最小限のコードを書く」 - 1ステップ
- 「パスすることを確認する」 - 1ステップ
- 「コミットする」 - 1ステップ

## 計画ドキュメントの構成
- **ゴール:** 構築する内容を 1 文で記述。
- **アーキテクチャ:** 採用するアプローチを 2-3 文で記述。
- **タスク構成:** コンポーネント、ファイル（新規/修正/テスト）、具体的なステップを記述。

# 大規模コードのモジュール化プロトコル (modularization-protocol)

## 概要
巨大なモノリス・モジュールを、保守性の高い「アトミック・エンジン」へと安全に分解するための技術手順。

## 1. 責務の抽出 (Responsibility Audit)
- 機能を **「知能（Heuristics/Logic）」** と **「管理（Orchestration）」** に分ける。
- `if/else` による分岐が多発している箇所を特定し、戦略パターンへの移行準備を行う。

## 2. 300行ルール (The 300-Line Rule)
- 1つの Python ファイル/クラスは、例外なく **300 行以内** に収める。
- これを超える場合、以下の役割に応じた分割を強制する：
    - `*_detector.py`: 物理/論理的な判定ロジック
    - `*_extractor.py`: 特定データの抽出・パース（Gemini API 等）
    - `*_constructor.py`: データの再構成・最終出力の構築

## 3. インターフェースの固定 (Data Model First)
- 分割後のモジュール間通信は、必ず `models.py` で定義された不変なデータモデルを介して行う。
- 巨大な辞書を渡すことを避け、型付けされたクラス（dataclass/Pydantic等）を活用する。

## 4. 段階的リファクタリング手順
1. **検証環境の固定**: 既存のテストがパスする状態を維持する。
2. **ユーティリティの独立**: 共通処理の移動。
3. **エンジンの切り出し**: ロジックの本体を `processor/` 配下の新ファイルへ移動。
4. **オーケストレーターの修正**: 元のファイルを、新エンジンを呼び出すだけの薄いラッパー（またはエントリポイント）に変更。
