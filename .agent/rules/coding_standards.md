# コーディング規約 (coding_standards.md)

本プロジェクトでは、「Superpowers」の設計思想に基づき、以下のコーディング規約を厳守します。

## 1. 300行ルール (The 300-Line Rule)
- 1つの Python ファイルまたはクラスは、原則として **300 行以内** に収める必要があります。
- これを超える場合、責務を適切に分割し、サブモジュール化を行ってください。

## 2. インターフェース先行実装 (Interface First)
- 複雑なデータ構造を扱う場合、実装の前に `models.py` でデータの「型」と「プロパティ」を確定させます。
- モジュール間は型安全なオブジェクト（dataclass 等）で会話してください。

## 3. モジュール分割の役割定義
- **Orchestrator (管理)**: 全体プロセスの制御、例外処理、進捗管理。
- **Detector (判定)**: 画像の傾き、見開きの有無、段組構成などの物理的・論理的判定。
- **Extractor (抽出)**: Gemini API 等を用いた、画像からテキスト・構造への変換。
- **Constructor (再構成)**: 抽出された断片を統合し、最終的なフォーマット（Markdown/Workflowy等）に組み立てる。

## 4. 高度な OCR パイプライン (Sequential V3)
- **文脈提示 (Context Awareness)**: 次の画像を抽出する際、必ず前ページの末尾テキスト（300文字程度）をプロンプトとして渡し、文章の接続を補助します。
- **物理レイアウト判定 (Moat & Break)**: 
  - **Moat (行間余白)**: 水平方向（縦書きの場合）に通常の3倍以上の余白がある行を見出しの候補とする。
  - **Break (行末断絶)**: ページの下端まで届かずに終わっている短い行を、段落末尾または見出しの兆候とみなす。
- **ノイズ除去**: 柱（ヘッダー）やページ番号、および物理的に隔離された脚注を「叙述の保全性」を妨げるノイズとしてスキップする。

## 5. エラーハンドリングとリトライ
- ネットワークや API レベルのエラーは、適切に指数バックオフリトライ（retrying/tenacity 等）を検討するか、`AsyncLimiter` を用いてレート制限を遵守してください。
- 各モジュールは独立して失敗可能（Graceful Degradation）な設計を推奨します。
