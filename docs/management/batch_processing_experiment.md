# 複数ページ束ね処理の実験記録（2026-07-21〜22）

## 1. 背景・目的

現行パイプラインは「1画像 = 1ページ = 1 Gemini APIコール」で処理している。無料枠（RPM=15, RPD=500）ではAPI呼び出し回数そのものがボトルネックになりやすいため、以下2案で「複数ページを1回のAPI呼び出しにまとめて、呼び出し回数を減らせないか」を検証した。

- **A) マルチパート方式**: 複数ページ画像を別々の `Part` として1リクエストに束ねる（ピクセルは結合しない）
- **B) ピクセル結合方式**: 複数ページ画像を1枚の合成JPEGに物理的に結合してから送る

Bについては、検討段階でGemini API公式ドキュメント（[media-resolution](https://ai.google.dev/gemini-api/docs/media-resolution)）を確認し、画像1枚あたりのトークン予算が固定（`media_resolution`未指定時で約1,120トークン/枚）であることが分かっていた。つまり複数ページを1枚に結合すると、ページ数が増えるほど1ページあたりの実効解像度が下がるリスクが理論的に想定された。

## 2. 実験の過程で見つかった既存バグ2件（束ねとは無関係、副産物）

実験環境を構築する過程で、束ね方式とは無関係な既存の不具合が2つ見つかり、修正した。**これらは束ね機能を採用するかどうかに関わらず有効な修正であり、現在もコードに残っている。**

### バグ① `thinking_level` パラメータがSDK非対応
`processor/gemini_extractor.py` の `ThinkingConfig(thinking_level="LOW")` が、現在PyPIで配布されている google-genai SDK（1.47.0、2026-07時点で最新）では `pydantic.ValidationError` になり、**素の状態では全てのOCR呼び出しが即座に失敗する**状態だった。公式ドキュメントのコード例は `thinking_level` を使う形になっており記述自体は正しいが、SDKのリリースが追いついていないと見られる。

- 対処: `thinking_budget=512` に変更（`thinking_level="LOW"` の代替として、小さめの正の値を使用）
- 注意: `thinking_budget=0`（完全無効化）は `temperature=0.0` と組み合わせると同一フレーズを数万文字繰り返す暴走が実測で複数回再現したため使用していない。

### バグ② 見開き左右分割（`find_gutter_x`）の信頼性判定が厳しすぎる
`docs/management/troubleshooting_log.md`（2026-04-01欄）に「一部PDFで綴じ目検出の安全策が発動し、分割されない」ことは既知の課題として記録されていたが、実データで検証したところ`morita.pdf`は4見開き中3つ、`matsumura.pdf`は5見開き中5つで分割に失敗しており、**「一部」ではなくほぼ常に失敗**していた。

原因を調べると、検出された綴じ目候補列は実際には理論値ちょうどの純白列（255×height）であることが多く、位置自体は正しいのに、「探索帯の平均に対して1.1倍以上明るいピークか」という相対判定のせいで信頼できないと棄却されていた（探索帯自体が既に真っ白に近いスキャンでは、この相対比が閾値を超えにくい）。

- 対処: `processor/image_detector.py` の `find_gutter_x` に、ピーク列がほぼ純白（99.5%以上）なら単独でも信頼できるという条件を追加。
- 影響: 見開き二段組ページでは、左右分割の失敗が上下（Top/Bottom）分割と組み合わさることで**読み順そのものが崩れる**実害があった（右ページ上段→左ページ上段→右ページ下段→左ページ下段、の順になるべきところが、右ページ上段→左ページ上段だけを1画像にまとめてしまうことで誤った順序になる）。実画像で修正前後を目視確認済み。

## 3. マルチパート方式の実験結果

### 3-1. 一段組（morita.pdf）: 束ね枚数ごとの精度

`tests/experiment_batch_sizes.py` で、`thinking_budget=512` を統一した上でbatch_size=1/2/3/5を比較（安定版 `Sample/morita_ocr.txt` を基準とした文字列類似度）。

| batch | 呼び出し回数 | 所要時間 | 精度(vs安定版) | 異常 |
|---|---|---|---|---|
| 1 | 5 | 26.8s | 98.2% | なし |
| 2 | 3 | 23.9s | 98.4% | なし |
| 3 | 2 | 22.3s | 96.0% | なし |
| 5 | 1 | 20.3s | 73.3% | ページ境界検出失敗 |

→ **2枚までは精度劣化なし、3枚から劣化、5枚は破綻**という明確な閾値が見えた。

### 3-2. 二段組（matsumura.pdf）: batch1 vs batch2 の直接比較

当初「二段組はbatch2で91%まで精度が落ちる」と見えたが、これは安定版ファイル（別バージョンで生成された可能性）との単純比較によるノイズだった。batch1とbatch2を同条件で直接生成して比較したところ、**両者は97.5%相互一致**しており、束ね自体による劣化ではないと判明。安定版との差が大きかったページも、実際は「本文と広告ブロックの掲載順序の違い」で、batch1・batch2どちらでも同じように発生していた（束ねとは無関係にモデルが物理レイアウトを再構成する挙動）。

### 3-3. 無料枠でのタイミング検証

理論上は「RPM=15の下で1リクエストあたり最低4秒の間隔が強制される」ため、呼び出し回数がそのまま処理時間に直結するはずだが、実測では:
- ページ境界マーカー不一致時のフォールバック（当初5回リトライしてから個別呼び出しに切替。無駄が多く2回に短縮）
- Gemini API側の既知のレイテンシスパイク（`docs/gemini_models.md` §6にも記載のある現象）

により、batch1とbatch2の所要時間がほぼ同じ、あるいはbatch2の方が遅くなるケースも観測された。**理論上の優位性が、実運用のノイズで簡単に相殺される**ことが分かった。

### 3-4. コスト

morita.pdfのトークン数実測（gemini-3.1-flash-lite: 入力$0.25/1M、出力$1.50/1M）:

| | batch1 | batch2 |
|---|---|---|
| 入力token | 7,704 | 6,786 |
| 出力token | 2,630 | 2,728 |
| 概算コスト | $0.00587 | $0.00579 |

差は1.4%程度で、実質的に無視できるレベル。

## 4. ピクセル結合方式（stitch）の実験結果

`tests/experiment_pixel_stitch.py` で、morita.pdf（gutter修正後8ユニット）を対象に、マルチパート方式と同条件（同じユニット組み合わせ、`thinking_budget=512`）で比較。

| 方式 | 呼び出し | 時間 | 入力token | 出力token | 精度 |
|---|---|---|---|---|---|
| multipart n=2 | 4 | 41.1s | 10,909 | 2,777 | 98.3% |
| stitch n=2 | 4 | 36.5s | 6,409 | 2,735 | 97.9% |
| multipart n=4 | 2 | 32.6s | 9,730 | 2,734 | 79.5% |
| **stitch n=4** | 2 | **286.2s** | **3,200** | **130,837** | **14.1%** |

事前の理論的懸念どおりの結果になった。stitch方式の入力トークン数は、2枚結合(6,409)でも4枚結合(3,200)でもほとんど変わらない＝**画像1枚あたりのトークン予算は結合前のページ数によらずほぼ一定**であることが実測で裏付けられた。4枚結合では実効解像度が本文を読み取れないレベルまで圧縮され、暴走（同一フレーズの大量反復、出力13万トークン超）が発生し、精度は14.1%まで崩壊した。

2枚結合(stitch n=2)は動作こそするが、multipart n=2に対して明確に勝る利点はなかった（トークンは削減されるが精度・呼び出し回数は同等）。

## 5. 結論と対応

- **束ね機能（マルチパート・ピクセル結合とも）は不採用**とし、コードから削除した。理由：
  - 精度面で明確な優位性がない（batch2は現行のbatch1相当と実質同等）
  - 呼び出し回数は減るが、実運用（フォールバック・API側レイテンシ）でその優位性が容易に相殺される
  - コスト差はごく僅か
  - ピクセル結合は3〜4枚で暴走するリスクが明確なため論外
- **バグ修正2件（①thinking_config、②find_gutter_x閾値）は採用・維持**。束ねとは独立した改善のため。

### ピクセル結合方式の画像合成ロジック（読み順を保つため先頭ユニットを右端に配置）

```python
def stitch_images(units_group, out_path):
    imgs = [Image.open(u["path"]) for u in units_group]
    max_h = max(im.height for im in imgs)
    resized = [im.resize((int(im.width * max_h / im.height), max_h)) if im.height != max_h else im for im in imgs]
    total_w = sum(im.width for im in resized)
    canvas = Image.new("RGB", (total_w, max_h), "white")
    x = 0
    for im in reversed(resized):  # 先頭(最初に読む)を右端に配置
        canvas.paste(im, (x, 0))
        x += im.width
    canvas.save(out_path, "JPEG", quality=90)
```
