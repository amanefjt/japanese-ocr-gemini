# Model Optimization Guide: Gemini 3.1 Flash シリーズ

本プロジェクトでは、2026年3月時点の最新かつ最もコストパフォーマンスに優れた **Gemini 3.1 Flash-Lite** を標準モデルとして採用します。

## ターゲット・モデル
- **標準モデル (MAIN)**: `gemini-3.1-flash-lite-preview`
- **思考レベル (THINKING_LEVEL)**: `LOW` (OCR 特化設定)

## 1. モデル選定の根拠

| モデル | RPD (無料枠) | コスト (Paid) | 採用理由 |
| :--- | :--- | :--- | :--- |
| **Gemini 3.1 Flash-Lite** | **500 RPD** | **極低価格** | 圧倒的なクォータ（500回/日）と低コスト。OCR精度も十分。 |
| **Gemini 3.1 Flash** | 20 RPD | 中コスト | 非常に複雑なレイアウトや手書き文字などの難易度が高い場合に使用。 |
| **Gemini 1.5 シリーズ** | 制限あり | - | **【廃止 / 役割終了】** 推論能力・コストの両面で 3.1 に劣る。 |

## 2. OCR 特化設定: Thinking Level "LOW"

日本語書籍の活字 OCR においては、最新の `thinking_level` パラメータをあえて **`LOW`** に設定することを推奨します。

- **理由**: 特定の活字ページで `HIGH` を使用すると、AIが「過剰思考（Overthinking）」に陥り、TTFT（最初の1文字が出るまでの時間）が170秒を超えるスパイクが発生することが技術監査で判明。
- **効果**: `LOW` を採用することで、精度を維持したままTTFTが平均約9秒→5秒へと高速化され、処理の安定性が劇的に向上します。

## 3. 最新の価格体系 (Paid Tier)

Gemini 3.1 シリーズの価格（プレビュー版、100万トークンあたり）は以下の通り、以前よりも大幅に引き下げられています。

| 項目 | **Gemini 3.1 Flash-Lite** | Gemini 3.1 Flash |
| :--- | :--- | :--- |
| **入力 (テキスト/画像)** | **$0.075** (約 11 円) | $0.50 (約 75 円) |
| **出力 (テキスト)** | **$1.50** (約 225 円) | $3.00 (約 450 円) |

*※ $1 = 150円換算。*

### コスト試算: 文庫本1冊 (100見開き / 200ページ)
- **総入力トークン**: 約 260,000 tokens ($0.0195)
- **総出力トークン**: 約 64,000 tokens ($0.096)
- **合計コスト**: **約 17.3 円** ($0.1155)

文庫本1冊を丸ごと V3 パイプライン（文脈提示あり）でデータ化しても、**わずか20円以下** という圧倒的な低コストで運用可能です。

## 4. レート制限と並列実行

- **有料版 (Paid)**: 20並列 / 500 RPM (標準)。高速性を優先。
- **無料版 (Free)**: 3並列 / 15 RPM (安全)。安定性を優先。
- **自動調整**: `OCROrchestrator` は指定されたティアに応じてこれらの制限を自動的に適用します。
- **リミッターの位置づけ**: `GeminiExtractor.limiter`（`AsyncLimiter(rpm_limit, 60)`）は実測のRPM上限と一致する値でプロアクティブにペーシングしており、通常運用でこの上限に張り付いて429を引くことはほぼない（§5の実験参照）。RPD（無料枠500/日）はコード上で強制する専用リミッターを持たず、`OCROrchestrator.run()`起動時に表示するのみ。

## 5. 無料枠2モデル併用の実験（2026-07-22）

p2workflowy（`docs/superpowers/specs/2026-07-22-free-tier-multi-model-lite-pool-design.md`、
`docs/model_optimization.md`§6-7、いずれも `p2workflowy` 側）で確立した「`gemini-3.1-flash-lite`と
`gemini-3.5-flash-lite`はRate Limit（RPM/RPD/TPM）が完全一致だが使用量カウンタは独立」という知見
（gocr側 `docs/gemini_models.md`§4 の共通データでも同じ実測値）を、gocrに移植できるか検証した。
2つの独立した施策に分けて実装・評価している。

### 5.1 施策①: `ModelRotator`（無料枠の実質容量2倍化）— 採用・既定で有効

`processor/model_rotator.py` を新設。429/503検知時、`TierManager`のダウンシフト（PAID→FREE）より
**優先して**、同一キー内でもう一方のLiteモデルへforward-onlyで切り替える。プールを使い切って
初めて従来のダウンシフト+待機にフォールバックする。`OCROrchestrator.run()`冒頭で毎回プール先頭へ
リセット。

- リスクはほぼゼロ（429が起きない限り一切発動せず、通常経路の挙動を変えない）ため既定で常時有効。
- CLIの`--free`時、1日あたりの実質リクエスト上限を約500回→(枯渇時に)約1000回相当まで拡張できる。
- 実地検証（下記5.3）では429自体が発生しなかったため、切替の発火自体は今回のテストでは確認できて
  いない（ロジックは`ModelRotator`単体の手動テストで確認済み。p2workflowy側もユニットテストで別途
  検証しており、同じ設計のため信頼度は高いと判断）。

### 5.2 施策②: `--parallel-pool`（ページペア単位ラウンドロビン、速度改善）— 実装したが非推奨・既定OFF

p2workflowyのPhase4翻訳・Phase1 VLM OCRで採用された「429を待たずに最初から2モデルへ振り分けて
同時実行し、各モデル専用のレートリミッタでスループット自体を上げる」手法を移植。
`OCROrchestrator._run_paired_parallel()`で、無料枠時に限り2ページずつペアにして
`gemini-3.1-flash-lite`/`gemini-3.5-flash-lite`へ同時発行する。CLI `--parallel-pool`で明示的に
有効化する必要がある（既定OFF）。

**構造的なトレードオフ**: gocrのOCRは前ページ末尾300文字を文脈として次ページへ厳密に引き継ぐ設計
（`CLAUDE.md`のアーキテクチャそのもの）。ペア内の2ユニットを同時発行するため、ペア内2枚目は
「直前ページ」ではなく「1つ前のペア」の文脈しか使えない。p2workflowyの翻訳フェーズも同種の
トレードオフを許容しているが、そちらは「訳文のトーンが変わる程度」で済んだ。

### 5.3 実地検証結果（2026-07-22、`Sample/matsumura.pdf` 5ページ/18ユニット、`--free`）

| 項目 | 逐次（既定） | `--parallel-pool` |
|---|---|---|
| 所要時間 | 103.0秒 | **70.2秒（-31.8%）** |
| 429/503発生 | 0回 | 0回 |

速度面ではp2workflowyの実測（Phase4: -18〜30%、Phase1 VLM: -18%）と同水準以上の改善を確認した。

**一方、精度面で無視できない劣化を確認した**。ベースラインと`--parallel-pool`出力をdiffすると、
全110行中73行が変化（追加44行/削除・変更相当73行）。具体的には:

- `gemini-3.5-flash-lite`側で「社会理論」→「社会会理論」という同一文字重複の誤字が**5箇所**に
  系統的に発生（ベースラインでは0箇所）。
- ペア境界（文の継ぎ目）で段落が丸ごと重複挿入される、あるいは前後の段落が欠落する事例を複数確認。
  5.2で想定した「1ページ古い文脈」という理論上の副作用が、実際には単なるトーン変化ではなく
  内容の重複・欠落という構造的な破損として表面化した。

gocrは「一字一句の忠実な書き起こし」が核心的な価値であり（`processor/prompts.py`の
「叙述の保全性原則」）、翻訳のようにパラフレーズが許容される用途とは精度要件の性質が異なる。
このため、p2workflowyでは許容できたトレードオフが、gocrでは実害として顕在化したと考えられる。

### 5.4 結論・今後の扱い

- **①`ModelRotator`は既定で有効のまま維持**。無料枠のRPD/RPM枠を安全に拡張する効果があり、
  通常経路の挙動・精度に影響しない。
- **②`--parallel-pool`は既定OFF・実験的機能として温存**するが、精度優先の通常利用では
  使用しないこと（`--help`・`models.py`のコメントにも明記済み）。
- **リミッター数値のチューニング余地は今回なし**: 逐次モードの平均応答時間（約5.7秒/リクエスト）が
  ペーシング間隔（4秒＝15RPM相当）より長く、`rpm_limit`自体は逐次モードのボトルネックになっていない
  （上げても速くならず、実測の実上限と一致しているため下げる理由もない）。②の高速化は数値調整では
  なく「実際に2本同時に飛ばした」ことによるものであり、その代償として上記5.3の精度劣化を払っている。
- ②を今後も追求するなら、ペア内で文脈を共有させない設計（例: ページグループ境界でのみ並列化する等）
  への作り直しが前提になる。現状の実装のまま既定化することは推奨しない。
